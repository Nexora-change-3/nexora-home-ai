# Архитектура NEXORA DESIGN ENGINE

## 1. Принцип

Разделить дизайнерское мышление, визуальное распознавание, графическую генерацию и контроль качества. Ни один поставщик модели не должен владеть всем процессом.

## 2. Поток данных

`Original Photo + User Brief + Verified Measurements`
→ `Input Validator`
→ `Vision Analysis`
→ `Constraint Model`
→ `Design Brain`
→ `Design Brief (JSON)`
→ `Concept Planner`
→ `Render Orchestrator`
→ `Model Adapter`
→ `Generated Candidate`
→ `Quality Gate`
→ `Results + User Review`

Каждый этап сохраняет версию входных данных и результат. Изменение концепции не должно менять оригинальную фотографию.

## 3. Модули

### INPUT
Принимает:
- оригинальное фото;
- тип помещения и его назначение;
- пожелания пользователя;
- реальные размеры, если известны;
- обязательные ограничения и то, что разрешено менять.

Проверяет формат, размер, наличие изображения, согласованность единиц измерения. Не придумывает отсутствующие размеры.

### VISION
Формирует наблюдения, а не окончательные проектные решения:
- границы видимых стен, пола и потолка;
- окна, двери, проёмы и неподвижные элементы;
- мебель, техника и предметы;
- приблизительная глубина/перспектива, если доступна соответствующая модель;
- области неопределённости и confidence.

Результат vision — гипотеза с уверенностью. Неизвестная геометрия не превращается в точное измерение.

### CONSTRAINT MODEL
Хранит раздельно:
- `fixed`: нельзя перемещать/изменять;
- `preserve`: сохранить насколько возможно;
- `replaceable`: разрешено заменить;
- `unknown`: требуется подтверждение.

Приоритет: явное указание пользователя > подтверждённый замер > визуальная оценка модели.

### DESIGN BRAIN
Создаёт полноценную концепцию до рендеринга:
- пространственная идея и композиция;
- планировочная логика;
- мебель и встроенные элементы;
- материалы и отделки;
- палитра;
- освещение;
- хранение и эргономика;
- визуальные акценты;
- объяснение дизайнерского замысла;
- риски и неразрешённые ограничения.

Генерирует несколько концепций с различными стратегиями, а не косметические вариации одного решения.

### CONCEPT PLANNER
Обеспечивает содержательное различие вариантов. Для каждой концепции фиксируются:
- уникальный тезис;
- план изменений;
- основные материалы;
- цветовая стратегия;
- мебельная стратегия;
- световая стратегия;
- что остаётся общим из архитектуры.

Варианты не должны отличаться только оттенком фасадов или случайным декором.

### MODEL ADAPTERS
Изолируют API и особенности каждого провайдера. Общий контракт описан в `../model-adapters/CONTRACT.md`. Поставщик модели может быть заменён без переписывания Design Brain.

### RENDER ORCHESTRATOR
Управляет:
- выбором адаптера;
- подготовкой изображения/масок/контрольных карт;
- количеством попыток;
- seed и параметрами, если поддерживаются;
- тайм-аутами и ошибками;
- сохранением метаданных;
- повторным запуском с тем же заданием.

Нельзя незаметно менять prompt, фото или параметры между сравниваемыми моделями.

### QUALITY GATE
Два слоя:
1. Автоматические проверки: валидность файла, визуальные признаки структурного дрейфа, соответствие маскам/контрольным картам, повторяемость и наличие результата.
2. Человеческая оценка: красота и профессиональность дизайна, удобство, правдоподобие, соответствие запросу.

Автоматический score не заменяет пользовательскую приёмку.

### RESULTS / EVALUATION
Сохраняет исходник, brief, концепцию, версию модели, параметры, результат, автоматические замечания и пользовательскую оценку. Старые неудачные генерации V1 не импортируются.

## 4. Геометрия и точность

Фотография одной перспективы не даёт достоверных размеров комнаты. Система должна явно маркировать неизвестные величины. Для реальных площадей, объёмов и смет в будущем потребуются проверенные размеры/план/скан и отдельный детерминированный расчётный модуль.

Для структурного контроля предусмотреть подключаемые методы:
- segmentation masks;
- edge/line maps;
- depth maps;
- ControlNet или эквивалентные пространственные условия;
- локальные маски редактирования;
- при наличии данных — 3D/room representation.

Ни один из этих методов сам по себе не гарантирует сохранение геометрии.

## 5. Критические инварианты

- Оригинал неизменяем.
- Все результаты имеют связь с оригиналом и версией задания.
- У каждого запуска фиксируются модель и параметры.
- Неизвестные размеры не выдаются за измеренные.
- Критические нарушения геометрии/назначения помещения означают отказ.
- Три концепции должны быть семантически различными.
- Production и ветки V1/V2 вне области этого эксперимента.
